From a click to a saved record

How SwapLabs works.

SwapLabs uses a multi-page frontend and a Python Flask backend. Pages are ordinary HTML files. Shared CSS gives them a common appearance, and JavaScript adds navigation, preferences, forms, search and asynchronous updates. Flask serves both the pages and the application’s JSON API from the same address.

  1. BrowserLoads HTML, shared styles and JavaScript.
  2. RequestA form or interaction calls a same-origin API using Fetch.
  3. FlaskChecks identity, permissions and inputs, then reads or updates records.
  4. ResponseReturns JSON; the interface renders the result or a clear error.

Why the server matters

Opening an HTML file directly only opens the frontend. Account saving, messaging and other persistent features need the Flask application. The default local address is http://127.0.0.1:8000. Both frontend and API use relative, same-origin URLs, so a supported port change applies to the whole app rather than requiring separate API addresses.

How records are stored

The current datastore is a server-side JSON file, data/users.json. It contains account information and collections for the supported features. Uploads are stored separately on disk. The Python process uses a lock to coordinate access and writes through a temporary file followed by replacement. This reduces partially written files, but it is not a substitute for a transactional database across multiple server processes.

What stays in the browser

Some interface preferences and local helper state use localStorage. That storage belongs to the current browser and device; it is not account-wide cloud storage. Server-backed settings and records use API requests. The interface should not describe a local-only selection as a real enrollment, booking or submitted report.

The connected features

What happens inside the main workflows.

Accounts, profiles and preferences

Registration and login are handled by the server. Passwords are checked using Werkzeug password-hashing utilities rather than stored as readable passwords. Flask’s signed session cookie identifies the session; signing protects integrity, not secrecy. Account and administrator permissions are checked on protected routes. Write requests use a CSRF token to help prevent another website from submitting actions through a signed-in browser.

Profiles store teaching skills, learning interests, location preferences, language, timezone and other settings. Visibility rules limit what another member can see. Profile editing shows unsaved changes, a saving state and confirmation after a successful response. A departure warning helps prevent accidental loss of edits; a failed save leaves the edits available to retry.

Skill discovery and explainable matching

Discovery reads public profile and offer records. Matching runs in Python and compares the learner’s needs with eligible members. It uses explicit rules rather than a trained recommendation model: skill fit, learning goal, teaching style, session format, schedule overlap, language, proficiency, session history and reliability. Each result includes the points awarded and explanations. These are compatibility scores, not a proven percentage chance of success.

The current maximum weights are 35 for skill fit, 10 each for goal, style and format, 15 for shared availability, 8 for language, 5 for proficiency, 4 for session history and 3 for reliability. A strict search can exclude weak skill matches. Availability comparisons use timezone-aware windows over the next eight days. Missing history is disclosed rather than replaced with invented reviews.

Inbox, groups and safety

Conversations and messages are persisted on the server. Access checks determine which participants can read a conversation or attachment. The interface supports operations such as unread indicators, typing updates, blocking, reporting and group management. Message updates use repeated HTTP requests rather than a WebSocket service. A report creates a record for administrator review; it is not an automatic guarantee of resolution.

Student-account safeguards include age-derived restrictions, private profile defaults and guardian-consent review fields. These are application safeguards, not proof of identity or a guarantee of safety. Administrators still need to review concerns and apply appropriate policies.

Calendar, workshops and video

Signed-in members can publish a workshop from Host a workshop. The server checks the title, future start time, IANA timezone, duration, capacity and learning outcomes, and assigns the signed-in member as host. Each newly hosted workshop creates one shared calendar event and meeting thread. Reservations add attendees to that event; cancelling one place leaves other attendees booked. The host manages the schedule, cancellation and completion through Calendar, with changes reflected in the workshop listing. Existing workshops and accounts are retained.

Calendar records store participants, start and end times, timezone, reminders and changes. Times are normalized and converted for display. Workshop registration records capacity and attendance-related state. A background reminder worker creates platform notices when due. Calendar export uses ICS files and Google/Outlook event-composer links; it is not two-way OAuth calendar synchronization.

Video rooms use browser media APIs and WebRTC. Camera and microphone access require browser permission. Flask handles room permissions and exchanges connection-signaling data; peer connections carry the media. Network conditions can require configured STUN/TURN infrastructure, and large calls would require a different media-server architecture. A successful page load alone does not verify video connectivity on every network.

Time credits and participation points

Time credits are internal exchange units, not currency or a bank account. The ledger stores payments, earnings, adjustments and refunds with references and resulting balances. A transfer checks the amount and balance before recording the outgoing and incoming entries. Disputes are reviewed through administrator tools. Corrections create further entries rather than silently rewriting the original transaction. Merely passing a scheduled end time does not prove an exchange occurred or automatically settle a payment.

Participation points are separate from the time-credit balance. The current code includes a monthly member-point grant and rewards for supported participation actions. A rule such as a grant amount is a configured product rule—not a statistic claiming that people have already participated.

Innovation, marketplace and learning records

The innovation area stores member proposals, comments and support activity, with additional review handling for student submissions. Marketplace records support offers and purchases in internal credits. Funding pledges record expressions of support; no payment processor transfers money. The learning journal stores a member’s own reflections and practice minutes. Achievements are calculated from recorded account activity; they are not accredited certificates.

Feedback, newsletters and administration

Feedback is saved with a publication-permission choice. Public testimonials include only permitted public fields; an email address is not included in the public testimonial response. Newsletter sign-up validates the email and consent, saves it, and exposes the list only to administrators. The administrator can copy addresses and send updates manually. The website does not claim to have sent an email just because a subscription was recorded.

The admin panel provides account controls, content review, reports, disputes, recorded-data charts and the newsletter list. Administrative actions are logged. The charts are drawn using the browser’s Canvas API, with values calculated from records—not preset decorative datasets.

SwapBot: a local website guide

SwapBot matches questions to a local knowledge base of website topics using keywords and spelling similarity, then returns guidance and relevant links. It is not the same as the AI tools used to build this project. The current implementation does not use a general cloud language model for these answers, and it should not be treated as an expert or a source of verified personal advice.

An honest data policy

Recorded numbers, clear limits.

Existing content, including starter workshops, ideas and feedback, is preserved and displayed. Public summary numbers come from /api/platform/metrics, and public record cards come from /api/public/content. Visible summaries refresh every 30 seconds while the page is active and refresh again when the user returns. This is polling-based freshness, not a claim of instant streaming.

Registered active accounts
Non-administrator accounts whose status is active; includes existing starter accounts. This is not a count of people currently online or recently active.
Publicly listed skills
Distinct skill names from eligible public profiles and published offers. This is a catalogue count, not a claim of verified expertise.
Countries
Distinct countries shared by eligible public profiles that permit location display. Private location details are not used for this public total.
Public groups and private group chats
Public community groups are counted separately from private inbox group chats. Private chat totals reveal no names, messages or members. A public group’s linked chat is not counted twice. All saved public groups remain available, including the original starter groups.
Confirmed completed sessions and hours
After a session’s scheduled end, its host or an administrator can confirm completion from Calendar’s “Awaiting confirmation” list. This records the confirmer and time, notifies participants and updates session counts, reputation and achievements. Repeated confirmation does not double-count. Hours use the scheduled start and end times, not independently measured attendance. Confirmation does not transfer credits, and completed records cannot be edited or cancelled.
Public feedback rating
The average of actual published site-feedback ratings with publication permission. It is not a teacher rating or a session-success rate.

Zero means a measured empty collection. “No data yet” means an average has no ratings. “Unavailable” means the statistics request failed. “Compatibility error” means required statistics are missing or invalid: restart the updated server and refresh. Saved accounts and content are included regardless of starter IDs. These are counts of saved records, not claims that every entry is independently verified or organically created. Historical records are retained, not deleted.

Pages without a connected course catalogue, formal certification service or published resource collection state that limitation. Fabricated participation totals, outcomes, testimonials and progress bars have no place as evidence of actual activity.

Built on shared technology

Tools, libraries and standards.

HTML, CSS and JavaScript
The frontend uses native web technologies: semantic page structure, responsive Grid/Flexbox layouts, shared design tokens, DOM events and Fetch requests. It does not use React, Vue or Tailwind as its application framework.
Python
Runs the backend and application logic. Standard-library modules handle JSON, dates, timezones, files, CSV exports, random tokens, locks, temporary files and matching text. Python’s virtual environment and pip support isolated dependency installation.
Flask and the Pallets projects
Flask supplies routing, requests, JSON responses, session support and static-file delivery. Werkzeug provides request-serving utilities and password hashing. Flask also depends on Jinja, MarkupSafe, ItsDangerous, Click and Blinker. Those dependencies are acknowledged even though this frontend primarily serves HTML files rather than rendering Jinja page templates.
Gunicorn and WSGI
Gunicorn is listed for supported production-style Python hosting. wsgi.py exposes the Flask app to a WSGI server. The local launchers use the Python application directly. The JSON datastore currently requires a single server process; adding workers is not a safe scaling shortcut.
ZoneInfo, tzdata and the IANA timezone database
Timezone rules support profile validation, scheduling and overlap calculations. The tzdata dependency supplies timezone data where the operating system does not, including typical Windows setups.
Boxicons and jsDelivr
Boxicons 2.1.4 supplies interface icons through the jsDelivr CDN. This is an external asset request, not an AI API. An offline or blocked CDN may prevent icon fonts from loading. Typeface styling requests Inter with system-font fallbacks; no separate Google Fonts service is required by the current stylesheet.
Browser APIs
Fetch communicates with Flask. FormData collects input and uploads. localStorage holds browser-local preferences. Canvas renders admin charts. MediaDevices and WebRTC support calls. ResizeObserver helps layout-aware navigation; the Clipboard API supports explicit copy actions. Browser capabilities and permissions affect availability.
JSON, HTTP, cookies and ICS
JSON carries API payloads and stores records. HTTP connects browser and server. Signed cookies support sessions. ICS exports calendar events. Google and Outlook links open their event-composer interfaces; they do not imply a connected account or background synchronization.
Development and testing tools
Python unittest and Flask’s test client exercise backend behavior using temporary records. Node.js runs JavaScript checks and focused tests; it is a development tool, not the website’s server. Codex’s browser tools assist with desktop/mobile viewport checks, screenshots and interaction testing. Shell tools support local startup and code inspection.

Third-party projects retain their own names, rights and licences. Acknowledgement is not a claim of endorsement or a replacement for licence compliance. No unverified payment, database, cloud-AI or analytics provider is listed as an active integration.

The website’s own API

The /api/ routes are SwapLabs application endpoints—not a collection of external paid services. For example, /api/auth/me describes the current session, /api/profile saves profile changes, /api/matches computes matches, /api/calendar returns permitted calendar information, and /api/credits returns the signed-in member’s ledger. Administrator routes require administrator access.

Forms send structured requests, wait for a successful server response and then render the saved state. Validation errors should explain why a request was rejected. Private API responses must not be copied into public statistics or exposed merely to make a page appear busy.

Still learning, still improving

What this project does not claim.

Automated checks cover selected authentication, privacy, messaging, scheduling, credit, newsletter, matching and settings behaviors. Passing tests is useful evidence, but not a guarantee of security, accessibility, performance or compatibility on every device. Desktop and mobile viewport checks are not the same as a full real-device test programme.

The application currently uses a local, single-process JSON datastore, disk uploads, polling-based updates and a rule-based guide. A larger public service would need further work on database transactions, deployment, backups, monitoring, email delivery and recovery, abuse prevention, accessibility and video infrastructure. No formal certifications, paid subscriptions or unconnected integrations should be presented as working services.

AI helped accelerate the build, but it also required checking and correction. The purpose of this page is to make the contribution and implementation understandable—not to hide assistance or overstate what has been built.
